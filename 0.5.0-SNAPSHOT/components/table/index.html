Table

Plain rows and cells

Section titled “Plain rows and cells”

<sl:table> styles the plain table elements you write inside it: caption, thead, tbody, tfoot, tr, th and td. There is no component per row or cell, as there is in shadcn/ui, so a row is the th:each you already write:

Attributes on <sl:table> go to the table; it sits in a container that scrolls sideways when the table is wider than the page. A table nested in a cell keeps its own look, so put it in an <sl:table> of its own.

Alignment

Section titled “Alignment”

<sl:table-head align="end"> puts a header’s label at the end of its cell. The cells below take the same with data-align="end" (or "center"), which works without utility classes, so also with the standalone stylesheet. Use it for amounts and other numbers, so their digits line up.

Sorting on the server

Section titled “Sorting on the server”

The rows of a Spring application live on the server, which sends one page of them. So a sortable header is a link that asks the server for the page in another order, not a script that reorders the rows in the browser:

<sl:table-head sort="name"> links to the same page with sort=name,asc, or sort=name,desc when the table is sorted by name ascending already. The link keeps every other parameter in the address (a search, the page size) and drops the page number, so a new order starts on the first page. The sorted column gets aria-sort, which screen readers announce, and an arrow; the others show both chevrons. A click on the sorted column reverses it; there is no unsorted state, because the default order is the controller’s.

The controller takes a Pageable, which Spring Data fills from those parameters, and puts the page in the model:

th:page takes the Page (or Slice), whose Sort tells the headers how the rows are sorted, the default from @PageableDefault included. Only the first sort key is shown. spring-data-commons is all it needs, not a Spring Data module: rows that do not come from a repository can be wrapped in a new PageImpl<>(rows, pageable, total).

Without th:page the headers read the order from the request’s sort parameter, so a table sorts without Spring Data too; the controller then reads that parameter itself.

Parameter names

Section titled “Parameter names”

The links use the parameter names your Pageable reads. Shadleaf takes them from Spring Boot’s properties: spring.data.web.sort.sort-parameter, and for the page and size links spring.data.web.pageable.page-parameter, size-parameter, prefix, qualifier-delimiter and one-indexed-parameters. If you configure Spring Data’s resolvers in code instead, declare a PagingParameters bean with the same values.

Limit what can be sorted

Section titled “Limit what can be sorted”

The sort parameter is part of the address, so anyone can edit it. Spring Data passes an unknown property on to the repository, which fails with an error page (?sort=password is an error at best). So the controller checks the order against the columns the table offers before it queries, and falls back to the default order when it asks for anything else:

The page the repository returns carries the order it was sorted by, so the table shows the fallback correctly too.

A stable order across pages

Section titled “A stable order across pages”

Rows with the same value in the sorted column (two people with 59 orders) come back from the database in no particular order, and not necessarily the same one for every page. Once the table has pages, such a row can show up on two pages, or on none. Add a unique key the reader does not see, such as the id, as the last sort key before you query:

The headers show only the first sort key, and the links are built from the request rather than from the page’s Sort, so the id never shows up in the address. Sample-01’s /people page does this, and its test follows Next from the first page to the last and finds every person exactly once.

Sorting an enum column

Section titled “Sorting an enum column”

An enum stored as a string (@Enumerated(EnumType.STRING)) sorts alphabetically: Admin, Guest, Member, Owner. To sort roles by rank, sort the database by the rank:

  • Store the rank. An AttributeConverter writes the enum as a number, so sort=role sorts by rank and the header needs nothing else. Sample-01 does this:

    An explicit rank, unlike EnumType.ORDINAL, survives reordering the enum’s constants.

  • Sort by an expression. Keep the string column and order by a CASE expression in a query of your own (order by case p.role when 'OWNER' then 1 when 'ADMIN' then 2 ... end), or with JpaSort.unsafe(...). The controller then maps the role property of the requested Sort to that expression, and the Page it gets back carries the expression, not role: build the page the template gets with the requested Pageable (new PageImpl<>(page.getContent(), pageable, page.getTotalElements())) so the header still shows the order.

Focus after an htmx swap

Section titled “Focus after an htmx swap”

Each sort link has an id (sort-name, or members-sort-name with a qualifier), so when htmx replaces the table it gives the focus back to the link that was clicked. Tables with htmx puts it together.

Search and filters

Section titled “Search and filters”

A search or filter above the table is a GET form the controller reads (?q=ada). Put <sl:query-params except="q"/> in it, so sending it keeps the table’s order and page size and starts on the first page; the sort and page links keep q by themselves. To search as the user types, see Tables with htmx.

Nothing found

Section titled “Nothing found”

<sl:table-empty> is the row to show when there are no rows: one cell across the table’s colspan columns, saying “No results.” (the message sl.table.empty, which your messages.properties can reword). Content of its own replaces the text.

Selecting rows

Section titled “Selecting rows”

For a bulk action (delete, change a role), give each row a checkbox of your own and put <sl:table-select-all/> in the header cell above them. Select-all checks or unchecks every row on the page, and is checked when they all are, indeterminate (a minus) when some are. <sl:table-selection-count> says how many are selected; place it where it fits, e.g. at the start of the footer, as shadcn’s data table does.

  • The rows are yours. Plain sl:checkboxes (name="ids", the row’s id as value) submit with the form, also without JavaScript; the controller gets @RequestParam List<Long> ids. The table can sit inside the form, or the checkboxes can name a form elsewhere with form="...".

  • Which checkboxes are rows. Select-all works on the checkboxes in the body cells of the table it is in (not of a table nested in a cell), leaving out disabled ones, which would not be submitted. When the body has other checkboxes too, name="ids" on select-all narrows it to those.

  • The selected look comes from CSS: a row whose first cell holds a checked checkbox gets the muted background (shadcn’s data-state="selected"), with or without JavaScript. Put the selection in the first column.

  • Names. Every row checkbox needs an accessible name, telling the rows apart. aria-label with the message sl.table.select-row (Select {0}) as above, or point at the cell that names the row:

    Select-all is named “Select all rows on this page” (sl.table.select-all); an aria-label of yours replaces it.

  • The count reads “2 of 20 selected” (sl.table.selection.count; keep {0} and {1} as they are, the browser fills them in). Its table prop is the table’s id, which sl:table puts on the table. It is not a live region: a row’s checkbox announces its own state, so the count is only announced after a click on select-all, which changes rows the user did not touch.

Without JavaScript

Section titled “Without JavaScript”

Select-all and the count need Alpine, so they keep their place but stay hidden until it starts (x-cloak). Without JavaScript the user checks the rows one by one, and the form submits them as before.

The bulk action

Section titled “The bulk action”

Post the form to the page’s own URL, query string included, so the action knows the search, order and page to come back to. The controller below puts that URL in the model; after the action it redirects back there with a toast (post/redirect/get):

Selection across pages

Section titled “Selection across pages”

Select-all selects the rows on the page, and a sort, another page or a new search (with htmx too) starts with nothing selected: the selection lives in the checkboxes, and those are replaced. Keeping it across pages is the server’s business. Two ways:

  • Keep the ids on the server, e.g. in the session: each page posts its selection (or a checkbox posts on change with htmx), and the page renders checked on the rows that were selected before. Select-all and the count then start from those.
  • Select everything that matches instead of ids: after select-all, offer “Select all 270 people”, which posts the search itself (q) for the action to apply to every match.

Sample-01 keeps the selection per page.

JavaScript

Section titled “JavaScript”

<sl:table-select-all> renders x-data="slTableSelection" and <sl:table-selection-count> x-data="slTableSelectionCount". They need no Alpine plugin. They follow the rows’ change events (Space or a click), a form reset, and rows being added or replaced (an htmx swap). Changing the rows from select-all fires input and change on every row it changes, as a click would.

Event On Detail
sl-table-selection-change the table, bubbling {selected, total}, after every change, and when select-all starts

A bulk action can listen to it, for instance to show how many people it would delete:

A checkbox of your own can be indeterminate too: set its indeterminate property, or render <sl:checkbox indeterminate>.

Left out

Section titled “Left out”

shadcn’s data table runs TanStack Table in the browser. These parts of it are not in Shadleaf: sorting and filtering in the browser, column visibility, resizing, reordering and pinning, drag handles, expandable rows, editable cells, virtual scrolling, selecting a range of rows with Shift and a click, and a selection that lasts across pages (see above).

Attributes

Section titled “Attributes”

sl:table

Section titled “sl:table”
AttributeValuesDefaultDescription
th:pageobject—The Spring Data Page or Slice the table shows. Its Sort tells every sl:table-head inside how the rows are sorted now. Without it, the headers read the order from the request's sort parameter.
qualifierstring—The @Qualifier of the controller's Pageable, for a second table on the page: its sort links use members_sort instead of sort.

Every prop can also be set from an expression: th:page="${...}". Any other attribute passes through to the rendered element, and class is appended.

sl:table-head

Section titled “sl:table-head”
AttributeValuesDefaultDescription
sortstring—The property to sort by, as the controller's Sort names it (name, address.city). Only the first key of the current order is shown.
alignstart center endstartWhere the label sits in the cell. Put the same data-align on the column's tds: end for amounts.

Every prop can also be set from an expression: th:sort="${...}". Any other attribute passes through to the rendered element, and class is appended.

sl:table-empty

Section titled “sl:table-empty”
AttributeValuesDefaultDescription
colspannumberrequiredThe number of columns the cell spans: all of the table's.

Every prop can also be set from an expression: th:colspan="${...}". Any other attribute passes through to the rendered element, and class is appended.

sl:table-select-all

Section titled “sl:table-select-all”
AttributeValuesDefaultDescription
namestring—The name of the row checkboxes, when the body has checkboxes of another kind too. Without it, every checkbox in a body cell is a row.

Every prop can also be set from an expression: th:name="${...}". Any other attribute passes through to the rendered element, and class is appended.

Section titled “sl:table-selection-count”
