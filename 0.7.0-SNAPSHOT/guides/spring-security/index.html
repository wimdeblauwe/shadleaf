Spring Security

Everything Shadleaf serves lives under /shadleaf/**: the stylesheet of each skin and the Alpine.js scripts, each with a content hash in its name. Permit that path for anonymous visitors, or every page they can see, such as your login page, renders unstyled:

The files are static resources inside the jar, so nothing else is exposed by it: the Vite manifest that maps names to hashed files is kept outside the served directory.

To run under a strict Content-Security-Policy as well, see CSP.

The signed-in user

Section titled “The signed-in user”

Templates read the signed-in user from #slUser, an expression object, so no controller has to add a user to the model, and error pages and fragments see it too. The user menu is built on it.

Expression Value
#slUser.signedIn Whether someone is signed in. Remember-me counts; an anonymous visitor does not.
#slUser.current The user (a ShadleafUser), or null for an anonymous visitor.
#slUser.current.name What to call the user. Never empty.
#slUser.current.username The name the user signs in with (GitHub’s login, OpenID Connect’s preferred_username, a UserDetails username), or null.
#slUser.current.email The email address, or null.
#slUser.current.picture The URL of a picture, or null.
#slUser.current.initials One or two letters for the avatar: the first and last word of the name (“Ludwig van Beethoven”: LB), or from the email.
#slUser.loginUrl Where Sign in goes, for @{...}.
#slUser.logoutUrl Where the sign-out form posts to, for @{...}.

Spring Security is an optional dependency of the starter. Without it #slUser is still there, and nobody is signed in.

Signing in with Keycloak or GitHub, and what each sends to the user menu, is in Signing in with OAuth2.

Where the user comes from

Section titled “Where the user comes from”

The default CurrentUserResolver reads what each kind of sign-in provides:

Sign-in Name Email, picture
OpenID Connect (Keycloak, Google, …) name, else given_name and family_name, else preferred_username, else the email email, picture
OAuth2 (GitHub) name, else login email (often missing), avatar_url
A JWT (resource server) as OpenID Connect, from its claims as OpenID Connect
Form login, HTTP Basic (UserDetails) the username none
Anything else Authentication.getName() none

htmx after the session expired

Section titled “htmx after the session expired”

When the session has expired, Spring Security answers an htmx request the way it answers a browser, and htmx cannot follow that:

  • A GET (a lazily loaded tab, a table’s rows, a dialog fetched into #modal-root) is redirected to the sign-in page. The browser’s XHR follows the redirect, and htmx swaps the sign-in page into the request’s target.
  • A POST fails its CSRF check, because the token lived in the session: a 403, which htmx does not swap. Nothing happens on the page.
  • After signing in the user is sent to the request Spring Security saved before it asked them to sign in. For an htmx request that is its URL, which may be a fragment endpoint that renders a few table rows as a page.

htmx-spring-boot (5.2.0 and later) has an entry point and an access denied handler that answer such a request with HX-Redirect to the page it was made from:

  • The page is the one the user is on (htmx’s HX-Current-URL), or for a boosted link the page it links to. The browser loads it as a normal navigation, the sign-in page asks the user to sign in, and the page is what they come back to, not the fragment.
  • A POST gets the same answer, but only when its CSRF token went with the session. A signed-in user without the required role still gets a plain 403, and so does a request with a wrong token.
  • Every request that is not an htmx request goes to the entry point you pass, so it behaves as before. With OAuth2 login, that is new LoginUrlAuthenticationEntryPoint("/oauth2/authorization/<registration id>"), the same URL as Sign in (see Signing in with OAuth2). If you have an access denied handler of your own, pass it to HxRedirectToPageAccessDeniedHandler, which hands every other denial to it.
  • /webjars/** is permitted so the sign-in page can load htmx, if your layout loads it there too.

Form input that was not sent is lost: the session that held the CSRF token is gone, so the POST cannot be replayed. An htmx request that needs a session made from a page anyone may see sends the visitor back to that page, still signed out; such a page should send them to Sign in itself.

Spring Security’s own suggestion, defaultAuthenticationEntryPointFor(entryPoint, htmxRequestMatcher), also works for htmx requests, but makes the htmx entry point the default for every request that does not ask for HTML (a fetch without an Accept header, a MockMvc test without accept(...)): those then get a 401 instead of the redirect to the sign-in page. The htmx-spring-boot README has the details, and how this combines with a sign-in form that is itself sent with htmx.

Sample-02 (samples/shadleaf-sample-02) has it: hx-boost on the body, a tab on its Data page that loads with htmx, and a form. Its SessionExpiryTest makes these requests without a session.
