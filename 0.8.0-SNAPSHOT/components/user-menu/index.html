User Menu

Usage

Section titled “Usage”

Put it in the sidebar’s footer:

It shows who is signed in, as Spring Security knows them: the user’s picture, name and email, in a large menu button (shadcn’s NavUser). The button opens a dropdown menu with the user at the top, then the items you put inside <sl:user-menu>, then Sign out. Without items there is nothing between the user and Sign out but a separator.

The user comes from #slUser (see Spring Security), so no controller adds anything to the model, and the menu works on every page, error pages included. The second line is the email, or the username when there is no email (GitHub often sends none) and it is not the name already (a form login’s user is named by the username), or nothing.

In the site header

Section titled “In the site header”

as="header" makes it a round button with the picture alone, for the end slot of a site header, as in the header layout:

The button has no text, so it is named “Account: “ and the user’s name: a screen reader says “Account: shadcn, menu button”. The menu opens below it, lined up with its end.

The picture

Section titled “The picture”

The picture goes through an avatar: while it loads, when the user has none and when it fails to load, the initials show instead (from the name, or from the email’s local part), and the user icon when there are no initials either. A picture that is gone, as an identity provider’s often are after a while, never shows a broken image.

Nobody signed in

Section titled “Nobody signed in”

For an anonymous visitor the menu is a Sign in link instead: a menu button with the log-in icon in the sidebar, an outline button in the header. It goes to #slUser.loginUrl: /login, the authorization endpoint of your one OAuth2 client (/oauth2/authorization/github), or what shadleaf.security.login-url says.

So one layout serves the sign-in page, a public page and the application. Without Spring Security on the classpath nobody is ever signed in, and the menu is always the link.

Signing out

Section titled “Signing out”

Sign out is a POST, with Spring Security’s CSRF token, to #slUser.logoutUrl: /logout, or what shadleaf.security.logout-url says. The menu holds only menu items, so the form is not inside it: <sl:user-menu> renders it after the menu, hidden, with the id user-menu-sign-out, and Sign out is a submit button in the menu that names it (form="user-menu-sign-out").

The form’s th:action is what adds the token, as on every form of yours; nothing to configure. Spring Security’s default /logout then signs the user out and redirects to /login?logout. With OpenID Connect, sign out at the provider too with Spring Security’s OidcClientInitiatedLogoutSuccessHandler: see Signing out at Keycloak.

hx-boost="false" keeps a boosted page from sending it with htmx: signing out should load a whole page, with a new CSRF token. The Sign in link has it too, as signing in usually redirects to an identity provider, which an htmx request cannot follow.

Where it opens

Section titled “Where it opens”

In the sidebar, the menu opens beside it (side="right"), its end lined up with the button’s: from the footer, it grows upwards. Collapsed to icons the button is the picture, with the name as a tooltip; the tooltip and the menu are never shown together. In the phone panel there is no room beside the button, so the menu opens above or below it, as every menu in the sidebar does. side and align change it:

Labels

Section titled “Labels”

{0} is the user’s name. An aria-label on <sl:user-menu as="header"> replaces the header button’s name for one menu. In the sidebar the button is named by the name and email it shows, and the Sign in link by its text, so an aria-label is left out there.

A different user menu

Section titled “A different user menu”

<sl:user-menu> covers shadcn’s NavUser. A menu laid out differently (another trigger, items above the user, a second group) is a dropdown menu of your own that reads #slUser:

Keep the form outside role="menu", and keep th:action: it adds the CSRF token.

A team or version switcher in the sidebar’s header is built the same way, from a dropdown menu: see Menus in the sidebar.

Without JavaScript

Section titled “Without JavaScript”

The menu is a popover, opened by the browser, so it opens and Sign out signs out without JavaScript. The arrow keys, typeahead and closing after an item need Alpine, as in every dropdown menu. Without JavaScript the picture lies over the initials and covers them once loaded.

Attributes

Section titled “Attributes”
AttributeValuesDefaultDescription
assidebar headersidebarsidebar: a sl:sidebar-menu with one large menu button, for the sl:sidebar-footer (shadcn's NavUser). header: a round button with the picture, for the end slot of sl:site-header, named "Account: " and the user's name.
idstringuser-menuThe menu's id. Its button gets the id with -trigger added, the sign-out form with -sign-out. Two user menus on a page need different ids.
sidetop right bottom left—The side of the button the menu opens on, as on sl:dropdown-menu-content. By default right in the sidebar (below the button in the phone panel) and bottom in the header.
alignstart center endendHow the menu lines up with the button along that side, as on sl:dropdown-menu-content.

Every prop can also be set from an expression: th:as="${...}". Any other attribute passes through to the rendered element, and class is appended.
