Forms with htmx

Shadleaf’s form components render plain HTML with every id, aria-invalid and aria-describedby in place, so a form that htmx swaps in is as accessible as one that loaded with the page. Shadleaf has no dependency on htmx and ships none of it; your application loads htmx, and the components pass hx-* attributes through like any other.

This guide follows the “Form with htmx” page of sample-01 (samples/shadleaf-sample-01, /htmx-form): it posts with htmx, comes back with its errors or a confirmation, moves focus to the right place, and still works as a normal POST without JavaScript. The sample’s /form page has the same fields without htmx, for comparison.

Loading htmx

Section titled “Loading htmx”

The sample uses htmx-spring-boot for the request and response headers, and htmx itself from its webjar, pinned in the pom:

  • A webjar, served by your application. It needs no Node build, and it comes from your own origin, so a policy with script-src 'self' allows it (add the nonce if your policy uses one). With webjars-locator-lite the template leaves the version out, and Spring Boot writes it into the URL (/webjars/htmx.org/2.0.11/...), which also busts caches on an upgrade. An application that bundles its JavaScript with Vite can import 'htmx.org' instead.
  • The config keeps htmx within a strict CSP. By default htmx adds an inline <style> for its request indicator, which style-src 'self' blocks, and evaluates hx-on handlers and js: values with eval. Turn both off unless you use them.

One form, two ways to post

Section titled “One form, two ways to post”

The form keeps its th:action and method="post", and gets hx-post next to them. htmx posts it when JavaScript runs; without it, the browser does. The part htmx swaps is a fragment that holds the form, or the confirmation:

hx:post (with a colon) is htmx-spring-boot’s Thymeleaf dialect: it resolves @{/form} like th:action does, and adds the CSRF header when Spring Security is on. hx-target is a plain attribute: # starts a message expression in Thymeleaf. The target is the fragment’s own wrapper, so the fragment replaces itself, and a second submit works like the first.

The controller answers an htmx request (it sends HX-Request) with the fragment alone, and everything else as before, with post/redirect/get on success:

  • Errors come back with status 200, as for the full page. htmx 2 does not swap 4xx responses unless you configure it to, so a 422 would need a responseHandling entry.
  • A valid htmx submit gets the confirmation, not a redirect. An htmx POST is not a navigation: a reload cannot send it again, which is what post/redirect/get protects against. An HX-Redirect (redirect:htmx:/form with htmx-spring-boot, flash attributes included) works too, but loads the whole page again, and focus with it.
  • Two handler methods with @HxRequest on one of them work as well, if you prefer that to the if.

Where focus goes

Section titled “Where focus goes”

When htmx replaces the form, the submit button that had the focus is gone, and focus falls back to the page. <sl:form-errors autofocus/> gives the server’s answer to where it should go, the same for both ways to post:

  • a global error, or any error with show="all": the summary, which the screen reader reads out;
  • field errors only: the first control with an error, which is read with its label, its invalid state and, through aria-describedby, its error;
  • the confirmation has its own tabindex="-1" and autofocus.

htmx focuses the first [autofocus] in content it swaps in. It first tries to put focus back on the element that had it, by id, so a user who pressed Enter in the name field would stay there; autofocus runs later and wins. See Form errors for the details.

Announcement

Section titled “Announcement”

The errors are announced because focus moves to them, so there is no role="alert" on the summary or the field errors, in the htmx response or anywhere else. A live region would read the same message a second time, and role="alert" on every field error would read all of them at once. The confirmation has no role="status" for the same reason: a live region inserted together with its text is not announced reliably anyway.

Add role="alert" when content changes without moving focus, for example a single field that htmx validates as the user leaves it: see Field.

Back button and history

Section titled “Back button and history”

hx-post pushes no history entry. The URL stays /form, and htmx’s history cache, which snapshots the page into localStorage when htmx pushes a URL, is not involved: back from another page shows /form as the browser kept it or as the server renders it again. If you boost navigation (hx-boost) or push URLs, htmx does snapshot pages, and a failed form keeps the user’s input in its value attributes. For a form with personal data, set "historyCacheSize": 0 in the htmx config, or hx-history="false" on the page.
