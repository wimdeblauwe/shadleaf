Field

One th:field for the whole field

Section titled “One th:field for the whole field”

Put th:field on <sl:field>, not on the control. The field reads the binding and hands it to its parts, so you write the field once and get:

  • the control bound to the field: name, value and id, as th:field on the control would give;
  • <sl:field-label> with a for that points at the control;
  • <sl:field-description> with an id, and the control’s aria-describedby pointing at it;
  • <sl:field-error> showing the binding’s messages, and the control described by them while there are any;
  • aria-invalid on the control and data-invalid on the field when the binding has errors.

Errors

Section titled “Errors”

<sl:field-error> renders nothing while the field has no errors. One message is shown as text, several as a list, each message once. Content of your own replaces the messages and always shows, so wrap it in a th:if when it should only show with errors.

The error has no role="alert". After a submit the whole page loads again, and a screen reader would read out every error at once. The control is aria-invalid and described by its error instead, so the message is read when the user reaches the control. When htmx swaps the whole form in, <sl:form-errors autofocus/> moves focus to the first control with an error, which reads it out; see Forms with htmx. If you swap a single field in while focus stays elsewhere, for example to validate it as the user leaves it, add role="alert" to its error yourself.

Errors that belong to the whole form rather than one field, such as reject(...) in the controller, go in a <sl:form-errors/> above the fields.

Ids

Section titled “Ids”

The control’s id is the field’s name, the id th:field gives a text input: email, or address.street for a nested property. The description and error ids add -description and -error. Set for on the field to use another id:

An aria-describedby you put on the control is kept, and the field’s ids are added after it.

For a checkbox or switch, Spring numbers the id (terms1), so that several checkboxes bound to one list field get different ids. In a field, the checkbox gets the field’s name instead, and the label points at it.

Radio buttons and checkbox groups

Section titled “Radio buttons and checkbox groups”

A set of options that answers one question is a <sl:field-set>, with a <sl:field-legend> as its question. th:field goes on the field set, and the options inside share it. A description and an error directly inside the field set describe the whole group: the fieldset gets the aria-describedby, while each radio button is still marked aria-invalid from the field.

For checkboxes, make each option a horizontal field without a th:field of its own. It takes the field set’s, and the next of Spring’s numbered ids (toppings1, toppings2), which its label points at.

variant="label" on the legend gives it the size of a field label; the default is a section heading.

Layout

Section titled “Layout”

<sl:field-group> stacks fields with even spacing. A field set without th:field groups related fields under a heading.

orientation="responsive" puts the label and the control side by side when the enclosing field group is at least 28rem wide, and stacks them when it is narrower.

Disabled and read-only

Section titled “Disabled and read-only”

A field notices a disabled control inside it and fades its label: there is no data-disabled to set, as there is in shadcn. The description keeps its colour, since it often says why the control is disabled.

disabled on a <sl:field-set> disables every control in it, as it does on any fieldset. The legend and the options’ labels fade with them.

A read-only control changes nothing in the field: its label stays as it is. See the input for how it looks.

A disabled control is not submitted, so an error on it usually comes from something the user cannot change in this form. It still shows: the control keeps its destructive border, faded, next to the field’s error. With <sl:form-errors autofocus/>, a control with a disabled attribute is passed over and the next control with errors takes the focus; one disabled by th:disabled or by a disabled field set is not known to be disabled when the page is rendered, and then nothing takes the focus.

Without th:field

Section titled “Without th:field”

A field without th:field is only layout. Set for to give the control its id, the label its for, and the description and error their ids. Without a binding, data-invalid and aria-invalid are yours to set.

How the parts find the field

Section titled “How the parts find the field”

<sl:field> renders its content with a local variable, slField, that holds the th:field, the ids and the messages. Every part and control inside it reads that variable, which is why nothing has to be repeated. To know whether it has a description or an error, the field looks at its content as written: a part added with th:replace is not seen, and a part with a th:if that is false still counts, so the control would point at a description that is not there.
